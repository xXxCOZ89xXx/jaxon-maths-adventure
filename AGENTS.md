## Current scope and ongoing architecture principles — owner approved

The private game is feature-frozen at `2d9cb055cbdda766349189a7f1017b31948d83e4`: nine worlds, 55 skills and 27 Practical Maths Town adventures. This section takes precedence over older implementation instructions below where they imply further development. Future commercialisation and hosting portability are planning requirements, not permission to implement commercial features. Keep the shortest safe route to private iPad play; do not initiate rebuilds, migrations, deployments, broad audits or new release preparation merely to satisfy these principles.

- **Portable hosting:** Keep the static application and build practical to serve on both Cloudflare Pages and Vercel. Avoid unnecessary provider-specific runtimes, storage or APIs for essential game behaviour. Keep hosting configuration separate from application code; document any unavoidable dependency and its replacement path.
- **Authentication and access:** Continue using the existing Supabase setup and server-enforced parent/learner permissions. Hosting access controls supplement application authentication; they must not become the family identity or authorisation model. Keep public browser configuration separate from server-only secrets and retain fail-closed environment checks. Any future commercial configuration needs separate approval rather than removing staging guards.
- **Families and children:** Design future extensions for independent families and multiple children per parent, with every selected learner authorised server-side. The current `v3_role()` contract requires exactly one matching relationship row, so multiple children per parent are not currently supported: adding another row alone is unsafe. Any future family/membership/profile design must explicitly preserve existing Auth identities, learner mappings, family links and permissions through a separately approved migration.
- **Preservation:** Preserve accounts, PINs, progress, revisions, balances, purchases, rewards, transaction/request history and immutable pending saves. Preserve storage namespaces and offline queue compatibility; future learner selection must scope caches and requests to the authorised learner. Never silently clear, truncate or overwrite saved or pending state to accommodate a new architecture.
- **Hosting moves:** Prefer a stable owner-controlled domain when practical. Browser storage belongs to its origin: a new hostname cannot automatically recover the old hostname's pending saves. Document and approve a sync/recovery plan before changing origins; do not discard queues or promise automatic local-data transfer.
- **Extensible learning content:** Keep content and activity definitions modular. When expansion is approved, prefer a registry with stable world, skill, question and activity IDs and content versions over scattered hard-coded counts or wording-based identity. Preserve existing IDs, mastery meaning, legacy validators and resumable journey snapshots; wording changes must not create false fresh mastery.
- **Progress growth:** Existing Town runs retain complete task snapshots and whole-progress saves use revision checks with a 2,000,000-byte server limit. Plan a compatible separation of current progress and retained history before growth reaches that limit; do not remove history or weaken concurrency/idempotency checks as a shortcut.
- **Future commercial boundaries:** Allow for trusted parent registration, family entitlements, free trials and subscription payments without implementing them now. Keep billing/subscription state separate from learning coins, parent rewards and mastery; payment events must eventually be verified and idempotent on the server. Subscription changes must never erase learning progress or grant access to another family.
- **Decision records and approval:** Document decisions that create provider lock-in, affect family isolation, change identity/content IDs, or alter saved-data compatibility. Record the reason, portability trade-off, preservation/migration impact and approval required. Database changes, commercial registration/billing, account changes, hosting project creation and publication require their own explicit owner approval; this guidance supplies none of those approvals.

## Non-negotiable safety and integrity
- Work on the existing `codex/v3-adventure-build` development branch. Do not commit to or merge into `main`; do not overwrite or replace `index.html` (the original live game) or the existing `v2-game-test.html` on `main`.
- Never authenticate as the real learner, run tests against the real learner's Supabase Auth identity, reset or alter the real learner's saved `maths_learning` record, or send test scores/rewards into production.
- A test account is **not** a reused browser session of the real learner. Tests must use local mocks/in-memory fixtures and, later if required, a separate staging Supabase project with dedicated parent and learner identities and their own family row.
- During automated tests, deny outbound network connections to the production Supabase host. Use test-specific keys/configuration and storage namespaces. Do not put credentials, service role keys, PINs, real learner identifiers, or downloaded personal data in the repository.
- Do not apply, migrate, drop, truncate, or alter any production Supabase schema. `supabase/v2-bonus-shop-migration.sql` is a **draft**, not approved or deployed. Preserve the secure server-side parent reward model and its role boundaries.
- Learning remains 60 active minutes per week, with 1 minute of active learning earning 1 minute of screen-time reward (10 min -> 10 min).
- Wrong answers, choosing "I don't know", and taking hints are safe and supported. Only independently correct fresh/spaced assessments can count toward independent mastery; do not award mastery from merely opening a lesson or clicking a game interaction.
- Do not create endless XP or coins from low-effort clicks, repeated reset loops, or immediate retakes. Keep gameplay fun and avoid time pressure, failure penalties, or public leaderboards.
