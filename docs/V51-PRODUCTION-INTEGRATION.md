Separate parent/child UNIQUE constraints imply at most one link per role per account. They do **not** prevent an account being a parent in one row and a child in another, including reciprocal links. Check this invariant privately before cutover; do not guess or automatically rewrite family links. Auth foreign keys confirm identity linkage, not actual row counts or valid password login.

## Security findings

1. **High priority: excess authenticated privileges on `learning_progress`.** Exports show SELECT, INSERT, UPDATE, DELETE, REFERENCES, TRIGGER and **TRUNCATE**. RLS applies to ordinary row operations; it does not constrain TRUNCATE. This is a genuine excess SQL privilege, but no exported callable truncation path establishes a remote browser exploit. Normal PostgREST table endpoints do not expose a TRUNCATE verb. Plan to revoke unnecessary privileges after dependency review; do not assume owner-only row policies neutralize them. DELETE is normally denied without an applicable policy, assuming no bypass/owner role; TRIGGER/REFERENCES also depend on other privileges and reachable interfaces. Confirm effective grants and exposed RPCs.
2. **Positive: sensitive family/reward tables have limited authenticated table grants.** Only SELECT is shown for families, rewards and events; progress has SELECT/INSERT/UPDATE. No client write policy for family links or reward counters is exported. Preserve this server authority. Broad `postgres`/`service_role` grants are expected privileged-role access, not evidence that browser clients have it. Service-role credentials must remain server-side. No anon table grants are shown; missing PUBLIC/inherited/column/sequence ACLs mean this is not proof of no effective anonymous access.
3. **SECURITY DEFINER requires full ACL/owner review.** Both reward functions use empty `search_path`, qualified app tables and `auth.uid()`/family checks: good defenses, with no dynamic SQL in the supplied bodies. Elevated ownership can bypass RLS, making those checks essential. Function owners, EXECUTE grants, role memberships and default privileges are not exported. PostgreSQL normally grants new functions PUBLIC EXECUTE unless revoked; do not assert that default still applies here. Explicitly audit/restrict signatures. Function input checks do not enforce a PIN, so an authorised parent's session could invoke them while the UI is locked.
4. **Legacy reward correctness gaps.** The non-`once` endpoint has no retry protection. The `once` body serializes matching parent/request retries and rejects altered non-null payloads, so absence of an exported request uniqueness constraint alone does not prove duplicate awards through that body. Its return is the current reward row, not the original stored response. No request-ID unique constraint is listed; a unique index could exist outside the export. Neither routine verifies available credited learning time before increasing `redeemed_minutes`. Neither is sufficient for V5.1's ledger.
5. **Null validation edge case.** Both bodies test `p_kind NOT IN (...)` without an explicit null check. SQL null makes that predicate unknown rather than true. A new null-kind request ultimately fails the non-null event insert and rolls back its counter mutation; do not report a confirmed persisted award exploit. In the `once` retry path, a null kind can evade the `<>` mismatch test and return an existing result without a new mutation. Future validation should explicitly reject nulls and use null-safe payload comparisons.
6. **Legacy paths bypass new PIN/CAS semantics.** `maths_learning` allows any authenticated caller to write a row keyed by its own Auth UUID without requiring that it is a linked learner; a parent/unlinked account can write its own separate row, not another child's row. It has no revision check. Existing SELECT policies and reward RPCs use Auth/family membership alone. Adding PIN-protected new APIs does not retroactively protect these old endpoints. Review/restrict legacy exposure during cutover; do not leave two independently writable reward authorities.
7. **Browser PINs are convenience locks.** Repository V2 source uses a per-device local PBKDF2 hash, while V3 uses server bcrypt. No database PIN store appears in the exports. A device hash cannot be converted to a bcrypt hash of the original PIN without the PIN; browser-local verification is not trustworthy server authorization. Preserve existing browser storage/configuration and Auth accounts. Any transition to a server PIN requires an explicit compatibility decision and recent password-authenticated enrollment; never silently reset PINs or upload/trust a browser hash as server proof.
8. **Historical trust is limited.** JSON learning fields are learner writable; they must not seed authoritative earned coins/time/ownership merely because the owner permits resetting learning. ON DELETE CASCADE would remove progress/reward history on account deletion, reinforcing why account recreation is inappropriate. Actual triggers, policies outside selection, RLS FORCE status and database role bypass attributes remain unverified.

## Recommended strategy: additive backend, preserved identities, single cutover

Keep `auth.users` and `maths_families` unchanged. Add the V3-named environment/PIN/unlock/progress/wallet/catalogue/transaction objects only after confirming no conflicts. Preserve the five exported legacy tables and reward events for rollback/audit. Use new V3 progress with fresh learning where approved; avoid complex learning imports when unnecessary.

Adopt **one post-cutover wallet authority** through `v3_request`; do not dual-write new wallets and old reward counters or casually wrap the old award RPC as a second writer. Privately reconcile and import the trusted parent bonus opening balance once, with a migration identifier/checksum and overwrite guards. Preserve reward events and existing redemption history. Missing purchase data in the exports means spending must be confirmed before treating total `bonus_coins` as available balance.

Legacy `redeemed_minutes` is not proof of credited earned time. Resetting learning while copying redeemed totals into a zero-earned wallet makes the available-time calculation inconsistent. **Do not fabricate matching earned activity or erase historical redemptions.** Recommended accounting proposal: preserve an immutable legacy redemption snapshot/history and start separately tracked V3 earned-time/redemption counters at cutover, with historical plus current totals presented distinctly. Implement only after reviewing whether any legitimate unredeemed entitlement exists; carry verified outstanding entitlement through an explicit opening-balance mechanism, not fabricated gameplay. This is an accounting compatibility decision, not covered by the learning-reset permission. If unresolved, block wallet activation rather than silently choose a balance.

Keep old PIN keys intact. If the bookmarked route uses only the local V2 PIN, a password-reauthenticated, explicit enrollment flow may let the owner enter the same known digits into the server PIN model; it cannot automatically guarantee the existing value. Confirm this transition before implementation. If an additional server PIN store exists elsewhere, inspect its schema/verification contract first and preserve it rather than assuming re-enrollment is needed.

At eventual cutover, retire or restrict the old browser write/reward/read routes as required by the reviewed PIN/data boundary, using a compatibility assessment of every deployed entry point. Save their definitions/ACLs privately for rollback. Revoke PUBLIC privileges as well as explicit role grants where necessary. Avoid orphaning an old page as a silently failing writer; it needs a deliberate retirement path at release time. No such source or ACL changes are authorised in this analysis session.
